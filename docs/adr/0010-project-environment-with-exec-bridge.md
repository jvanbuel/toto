# 10. Project-defined environment in the sandbox, reached through an MCP exec bridge

- Status: Superseded by ADR 13; was: Proposed (route prototyped; see "Verified")
- Date: 2026-10-04
- Refines: ADR 5 and ADR 9

## Context

Project owners should define the environment a task runs in (toolchain, tools, skills, MCP servers) and carry the burden of its contents, while the contributor's machine stays protected and the contributor's login never enters the sandbox (ADR 5, option "harness outside, task inside").

Omnigent cannot route command execution into an external sandbox, and its default mode puts the Claude login inside its own (ADR 5, findings). But Omnigent's runner starts the MCP servers of an agent spec as host child processes, and a spec with no `os_env` registers no host shell or file tools and keeps the CLI's native tools off.

## Decision

The agent loop and login stay outside the sandbox. The only tools the agent has run inside the task container, reached over MCP:

- The runner starts the task container (hardened: no network by default, read-only root, dropped capabilities, no host mounts except the read-only bridge binary).
- A small static MCP server, `toto-mcp-exec`, is mounted read-only at `/toto/mcp-exec` and provides `run_command`, `read_file`, `write_file` and `list_dir` inside the container.
- The runner generates the agent spec for Omnigent with no `os_env` and one MCP server, `sandbox`, whose command is `docker exec -i <container> /toto/mcp-exec`. The command line is always generated by the runner; the name `sandbox` is reserved and a project cannot shadow it.
- Project-defined MCP servers and skills are meant to run in the same container the same way. Projects declare the image (pinned by digest), the tools in it and the servers to start; the runner never takes a host command from a manifest.

What stays fixed whatever a project declares: no credentials in the container, no host mounts, no privileged mode or extra capabilities, network only to hosts the contributor's policy allows, no commands on the host.

## Verified (2026-10-04, Omnigent 0.16.0, no model calls)

- The bridge runs in the hardened container: tools execute as an unprivileged user, the root is read-only, there is no network, no host files, timeouts kill, and the bridge binary itself is read-only.
- Omnigent's own `RunnerMcpManager` launched `docker exec -i ... /toto/mcp-exec` from a parsed agent spec, listed its four tools and executed a call inside the container; nothing was written on the host.
- A spec without `os_env` leaves the CLI in no-native-tools mode.

- Task inputs and outputs (2026-10-04): standard tar. An input tar is hash-checked and strictly validated on the host (regular files and directories at safe relative paths only), then extracted in the container by plain `tar -x` (the image must provide `tar`). After the run, `tar -c` of `/workspace` is streamed to the host and compared against a baseline kept on the host; changed files come back as a tar with deletions as OCI-layer whiteouts (`.wh.<name>`). Verified in a live container, including that symlinks are never collected and malformed archives are refused, and against the system `tar` in both directions.

## Not yet verified

- A real model using the tools through Claude Code (needs a login).
- Project-declared images, in-container stdio MCP servers and skills placed in the container.
- Windows: relies on Docker Desktop's VM.

## Consequences

- One sandbox model for everything a project ships; the trust boundary is the container, not a list of allowed fields.
- The MCP stream from the container is parsed by the trusted harness, so a hostile container can attack through tool output (prompt injection) and the MCP protocol parser, but not through code execution on the host.
- Result review (ADR 6) stays important.

## Update (2026-10-04): the project names its image, through a dev container subset

The environment is now the project's, not the runner's: `.toto/project.json` names an image (directly or through the `image` key of a `devcontainer.json`), `toto projects add` records it in the contributor's `environments`, and the docker sandbox starts that project's tasks in that image, with the same hardening (read-only, no capabilities, unprivileged user, no network unless granted). The dev container spec is used only as the place to name the image: files that build an image or act on the host (`build`, `dockerFile`, `features`, `mounts`, `runArgs`, `privileged`, `capAdd`, `securityOpt`, `initializeCommand`, ...) are refused, since honouring them would act on the host or run a stranger's build before anything was approved (build steps run in a container with network; contained, but unreviewed); the project builds and publishes the image in its own CI. Images must be fully qualified with a tag or digest; digest pinning is not required. A missing image is pulled by the contributor's docker; `probe` checks every configured image. Owner guide: `docs/project-owner-guide.md`.

### Approval is bound to the digest (same day)

A tag can be moved after a contributor approved it, so the approval records the image **digest** and the runner starts `repo@sha256:...`. `toto projects add` shows what is being approved from the image itself (user, environment, entrypoint, size, the build step of each layer); `toto projects inspect` shows it, plus the project's `devcontainer.json`, without changing anything; `toto projects update` re-pulls the tag, diffs against what was approved and asks again. The digest is pinned automatically, so project owners publish tags and never handle digests. Limits: layer history lists commands, not file contents, and an image can look innocent, so approval is trust in the project plus isolation, not proof; verifying that an image was built from published source (signed provenance, for example Sigstore or GitHub artifact attestations) would be the real answer and is not built.
